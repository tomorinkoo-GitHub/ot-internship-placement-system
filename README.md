# 実習配置システム（GAS + ハンガリアン法） README

このドキュメントは、本システムを初めて読む人（人間・AIどちらも）が、コードを1行も読まずに全体構造・データフロー・運用ルール・既知の制約を把握できるようにするためのものです。他大学へ展開する際は、まずこのREADMEを読んでから `実習配置システム.gs`（または該当のコードファイル）を参照してください。

---

## 1. これは何か

作業療法士養成校における「学生 × 実習施設」のマッチングを自動化するシステムです。
Google Apps Script（GAS）+ Google スプレッドシートで動作し、内部でハンガリアン法（最小コスト割当アルゴリズム）を使って、学生と実習施設の組み合わせを「移動距離が最小になるように」自動決定します。

対象となる実習は5種類あります。

| 実習名 | 対象学年（デフォルト設定） |
|---|---|
| 早期体験 | 1年 |
| 見学実習 | 2年 |
| 臨床実習Ⅰ | 2年 |
| 臨床実習Ⅱ | 3年 |
| 臨床実習Ⅲ | 3年 |

※学年設定は `CONFIG.実習` で変更可能。他大学で学年構成が異なる場合はここを編集する。

## 2. 前提として必ず理解すべきこと（最重要）

### 2-1. 「学生数 と 施設の空き枠数」は一致しないのが通常運転
施設は年度途中でも追加募集をかけるため、**施設側の枠数が学生数を上回ることが常態**です。逆に枠が不足する時期もあります。どちらが多いかは実行時点によって入れ替わるため、コード側は「学生数と枠数、どちらが多いか」を前提にしてはいけません（v9.4まではここでクラッシュしていた。詳細は6章）。

### 2-2. 枠数・座標の正は「フォーム貼付」シート、施設マスタではない
`施設マスタ`は別ファイル管理・原則読み取り専用です。枠数（募集人数）や緯度経度は、実際にはフォーム回答が随時更新される `フォーム貼付` シートから直接読みます。施設マスタ経由でデータを転記する設計には**意図的に戻さないこと**（転記漏れによる事故を避けるため。v9.3で撤廃済み）。

### 2-3. 設計変更は「先に方針合意、後で実装」
このコードの開発ルールとして、実装前に必ずアプローチを議論してから着手する運用になっている。AIが引き継いで改修する場合も、いきなりコードを書き換えず、まず変更方針を人間（運用担当者）に確認すること。

## 3. 全体の運用フロー（年に1回まわす）

```
① セットアップ実行         … 全シートのヘッダーを作成/強制上書き
② 施設マスタ 緯度経度取得   … 施設マスタの住所→緯度経度・エリア判定
② 学生マスタ 緯度経度取得   … 学生の住所1・住所2→緯度経度（別列に分離書込み）
③ フォーム貼付を処理        … フォーム回答に施設IDを自動マッチング、住所/緯度経度を補完
④ （各実習）施設を展開      … フォーム貼付の残り枠数ぶん、配置シートに施設行を生成
   ↓ ここで手動配置が必要な学生を先に割り付け、ステータスを「手動配置」に変更
④ （各実習）配置実行        … 手動配置・確定を除いた残り全部をハンガリアン法で自動割当
⑤ 地図リンクを生成          … 学生住所⇔施設住所のGoogleマップ経路リンクを生成
⑥ 重複チェック・最終確認    … 同一学生×同一施設の重複がないか確認（視覚チェックのみ、自動排除はしない）
⑦ 需給管理を更新            … エリア別の枠数・学生数・過不足を集計
⑦ 確定配置を書き出し        … ステータス「確定」の行を年度付きで過去配置シートに保存
⑧ 就職説明会リストを生成    … 臨床実習Ⅰ〜Ⅲの施設から送付先リストを生成
```

これらはすべて、スプレッドシートのカスタムメニュー「🏥 実習配置」から実行される（`onOpen()` 参照）。

## 4. シート構成（データモデル）

| シート名 | 役割 | 備考 |
|---|---|---|
| 施設マスタ | 実習施設の恒久的な基本情報（別ファイル） | 原則読み取り専用。TEMP001のような仮IDで登録未了施設を管理可能 |
| 学生マスタ | 学生の基本情報・住所・希望領域 | 住所1（現住所）と住所2（実習中利用可能な住所）を別々に持つ |
| フォーム貼付 | 各年度の施設からのフォーム回答を貼り付ける場所 | 枠数・緯度経度の実質的な正データソース |
| 早期体験／見学実習／臨床実習Ⅰ・Ⅱ・Ⅲ | 実習ごとの配置結果シート | 1行＝1スロット（学生1名分の枠） |
| 需給管理 | エリア別の枠数・学生数・過不足の集計 | `需給管理を更新` で毎回作り直す |
| 配置ログ | 配置実行のたびに追記される実行履歴 | 未配置者リストも記録 |
| エリアマスタ | 市区町村→エリア名の対応表 | 初期データはコード内にハードコード |
| 過去配置 | 年度別の確定配置の保存先 | 「確定配置を書き出し」で年度分を上書き |
| 実習期間マスタ | 年度・学年・実習種別ごとの開始日・終了日 | 初期データはコード内にハードコード |
| 就職説明会_送付先リスト | 臨床実習Ⅰ〜Ⅲ施設への送付先リスト | 就職説明会案内用 |

### 4-2. 配置シート（実習ごと）の列
```
A:施設ID  B:施設名  C:施設住所  D:学籍番号  E:学生氏名  F:学生住所
G:直線距離(km)  H:移動時間(分)  I:地図で確認  J:ステータス  K:備考
```

ステータス値： `手動配置` / `自動配置` / `確定` / 空欄（未着手のスロット） / `未配置`（配置実行結果、枠不足で余った学生）

```

J:住所2（実習中利用可能） K:緯度2 L:経度2 M:エリア（住所2）
N:希望領域 O:備考
```

## 5. 重要な業務ルール・記法

- **「配置見送り」記法**：配置シートの `学籍番号` 列に手動でこの文字列を入力すると、自動配置がそのスロットをスキップする。
- **TEMP001方式**：施設マスタへの正式登録が済んでいない新規施設は、`施設ID` 列に `TEMP001` のような仮IDを振り、住所は手入力する。緯度経度取得はすでに値が入っている行をスキップする仕様なので、仮登録行が壊れることはない。
- **施設名の表記ゆれ吸収**：フォーム回答の施設名と施設マスタの施設名が完全一致しないケースに対応するため、4段階のあいまいマッチングを行う（完全一致→法人格プレフィックス除去後の一致→部分一致→逆部分一致）。マッチしない場合は施設ID欄が空欄になり、手入力が必要。
- **重複チェックは視覚のみ**：`重複チェック・最終確認` は同一学生×同一施設の重複を検出して警告するだけで、自動削除・自動排除はしない（意図的な仕様）。
- **セットアップの上書き注意**：`セットアップ実行` は全シートの1行目（ヘッダー）を毎回強制的に上書きする。既存データ行は消さないが、ヘッダー構成を変えた直後に実行すると列がズレる可能性があるため注意。
- **既知の未解決事項**：`施設を展開` を複数回実行した際、自動配置・空行は削除されるが、削除漏れが起きるケースがあるため、セットアップ直後の空行は手動で消す必要がある場合がある（自動クリア機能は未実装、要否は未確定）。

## 6. アルゴリズム設計上の重要な経緯（改修時に必読）

### 6-1. v9.4までのバグ
旧実装は「学生数と施設枠数のうち多い方に合わせて正方行列にパディングする」方式だった。ダミー値として `1e9` を使っていたが、これがハンガリアン法の探索内部で使う番兵値（比較用の閾値）とビット桁が被っていたため、**施設側の枠数が学生数を上回る（＝日常的に起きる）ケースでほぼ確実にクラッシュ**していた（`TypeError: Cannot read properties of undefined (reading '0')`）。

### 6-2. v9.5での解決（矩形ハンガリアン法）
`_矩形ハンガリアン法(cost)` は、**正方行列化を一切行わない**。呼び出し側（`_配置実行`）が、学生数とスロット数のうち少ない方を「行」、多い方を「列」として動的にコスト行列を組み立てる（`学生が行` フラグで判定）。これにより：
- ダミー行・ダミー列が発生しない
- コストのダミー値（`1e9`、緯度経度欠損時の距離未計算用）と、探索アルゴリズム内部の番兵値（`Number.MAX_SAFE_INTEGER`）が桁として完全に分離される
- 行数 ≤ 列数が構造的に保証されるため、全ての行（＝少ない方＝学生か施設のどちらか）が必ず割当てられ、`assignment` に `-1` が発生しない

改修時にこの関数へ手を入れる場合は、**「行数 ≤ 列数」の前提を絶対に崩さないこと**。崩すと v9.4 と同じクラス（正方化前提のバグ）が再発する。

### 6-3. デバッグの教訓
このバグの原因特定は、最初は「緯度経度欠損の行が怪しい」という仮説から入ったが、実際のブレークスルーは運用担当者が「特定の1施設の行でクラッシュする」という**観測事実**を報告したことだった。改修時は仮説より先に、まず「どの入力でどう壊れるか」の実測を最優先すること。

## 8. 他大学へ展開する際に確認・調整すべき箇所

1. `CONFIG.実習` の実習名・対象学年（学年構成が異なる場合は要変更）
2. `CONFIG.実習期間マスタ初期データ`（年度・日程はハードコードなので毎年 or 校ごとに更新が必要）
3. `エリアマスタ初期データ`（東京近郊の市区町村区分が前提。他地域では作り直しが必要）
4. `_法人格除去()` の法人プレフィックス一覧（地域や施設種別によって追加が必要な場合あり）
5. 施設マスタのファイルが別スプレッドシートである前提（`GoogleアカウントID`・`スプシファイルID` 列がある）。運用によっては同一ファイル内に統合したいというニーズが出るかもしれないが、現状は年度ごとにファイルを作り直す設計であり、複数年統合は移行リスクを理由に見送り中。

### 9-4. エリアマスタ（東京近郊以外で使う場合は作り直しが必要）

| エリア | 市区町村 |
|---|---|
| ①都心 | 東京都千代田区 |
